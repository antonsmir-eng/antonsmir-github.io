# Точный ремонт

Сайт независимого сервиса по ремонту стиральных машин, посудомоечных машин и кофемашин в Москве. Статические SEO-страницы + интерактивные помощники + отдельный Node.js API с SQLite. GitHub Pages публикует только публичную часть; API с данными клиентов размещается отдельно либо сайт целиком работает на одном сервере.

## Что реализовано

- Адаптивный дизайн, собственная иллюстрация, мобильное меню, клавиатурная навигация и reduced motion.
- 20 HTML-страниц, включая три отдельных направления ремонта: главная, услуги, инструменты, диагностика, проверка сметы, калькулятор, запись, блог, 5 статей, истории ремонтов, контакты, приватность, кабинет диспетчера; плюс 404.
- Диагностика по 18 основным симптомам для трёх видов техники. У новых направлений нет неутверждённых ценовых диапазонов. Подтверждённый стартовый справочник: LG OE, IE, UE, dE; для прочих кодов честное сообщение об отсутствии проверенной расшифровки.
- Распознавание текста кода по фотографии через Tesseract.js 6.0.1 в браузере, проверка размера/типа файла, ручное подтверждение результата. Это OCR, не определение физической поломки по снимку. Требуется доступ к CDN и загрузка языковой модели. При сбое остаётся ручной ввод.
- Проверка сметы: сумма работы, запчастей и прочих затрат, вопросы исполнителю. Фото сметы доступно для локального предпросмотра; автоматического извлечения сумм из документа нет.
- Калькулятор ремонта/замены с явными условными порогами; не прогнозирует ресурс машины.
- Блог с фильтрами и поиском; тексты доступны роботу без JavaScript, есть canonical, description, Article JSON-LD и sitemap.
- Серверная запись: телефон, согласие, фото, UTM, защита от дублей, идемпотентность, реально опубликованные интервалы, защита от двойного бронирования.
- Кабинет диспетчера `/admin/`: обращения, статусы, оплата, фото, CSV, интервалы мастеров, публикация текстовых историй реальных ремонтов.
- Метрика только при заданном ID и согласии. События `diagnosis_complete`, `estimate_complete`, `comparison_complete`, `lead_received`. Последнее означает полученное обращение, НЕ целевой лид. Статус `qualified` выставляет диспетчер.
- Генератор фида услуг актуального формата `services_feed`; отключён до заполнения настоящих данных. Команда IndexNow для новых/изменённых URL.
- GitHub Actions для тестов, сборки и GitHub Pages; Dockerfile для сервера.

## Текущее состояние

Рабочее название — «Точный ремонт». Владелец ещё не предоставил телефон, контакты, реквизиты, утверждённый прайс, расписание и сервер. Поэтому `bookingEnabled=false`: формы не отправляют данные и прямо сообщают, что приём закрыт. Нет фиктивных отзывов, мастеров, занятых/свободных окон, кейсов и статистики. Индексация предварительной версии отключена. Это полноценный код продукта, но не запущенный приём заказов.

Из обсуждавшихся маркетинговых механик код сайта реализует инструменты и инфраструктуру. Рекламные кампании, ретаргетинг в кабинете Яндекса, подача фида, подтверждение домена, создание аккаунтов аналитики и получение реальных отзывов не выполняются автоматически.

## Локальный запуск

Нужен Node.js 24+. Для основной сборки нет npm-зависимостей.

```sh
node build.mjs
node preview.mjs
```

Открыть `http://127.0.0.1:4173/antonsmir-github.io/washing-machine-service/`. Сервер preview предназначен только для локального просмотра, не принимает заявки.

Целевой адрес публикации: https://antonsmir-eng.github.io/antonsmir-github.io/washing-machine-service/ . В существующем репозитории публичная сборка размещается в `washing-machine-service/`, исходники — в `projects/washing-machine-service/`. Корневая страница другого проекта сохранена. Текущий корневой workflow публикует готовую сборку: после правок нужно выполнить сборку и обновить обе папки. Вложенный workflow в исходниках автоматически не запускается.

Исследование премиальных референсов и принятые решения: [DESIGN.md](DESIGN.md). Исследование 25 сайтов Москвы, ещё двух кофейных сервисов и внедрённые решения: [RESEARCH.md](RESEARCH.md). Общая тема интерфейса — `public/assets/premium.css`, новые сценарии и категории — `public/assets/conversion.css`.

```sh
node --test tests/*.test.mjs
```

## GitHub Pages

1. Создать репозиторий `washing-machine-service` в аккаунте владельца.
2. Загрузить исходники, включая `.github/workflows/pages.yml` и `public/assets/hero.webp`. Не загружать `.env`, `data`, базы SQLite и клиентские сведения.
3. В Settings → Pages выбрать Source: GitHub Actions.
4. Push в `main` запускает тесты, сборку и публикацию.

Для другого имени репозитория изменить `basePath`, для другого аккаунта — `origin` в `site.config.json`. Для собственного домена `basePath` обычно пустой. GitHub Pages не запускает Node.js и не сохраняет заявки; на нём нужна ссылка `apiBase` на отдельный HTTPS API. Аккаунт GitHub и публикация должны быть проверены отдельно, наличие workflow не означает успешного деплоя.

## Включение настоящего приёма заявок

1. Заполнить `name`, `phone`, `email`, `legalName`, `legalAddress`, `inn`, при необходимости `telegram` в `site.config.json`.
2. Проверить мастером справочник и ориентиры в `src/data.mjs`, утвердить цены (`pricesApproved=true`), условия выезда, диагностики и гарантии; обновить тексты страницы услуг. Сейчас цены — предположения, а не утверждённый прайс.
3. Подготовить применимую политику обработки данных в `src/pages.mjs`, включая сроки хранения, контакт оператора, порядок отзыва согласия и удаления. Нынешняя страница объясняет закрытый режим, не подменяет готовую политику действующего бизнеса.
4. Разместить API на выбранном владельцем сервере с HTTPS и постоянным диском. Для персональных данных клиентов выбор места хранения и регламент обработки необходимо определить до запуска.
5. Указать публичный адрес API в `apiBase`, разрешённые источники сайта — в `ALLOWED_ORIGINS`. Секрет `ADMIN_TOKEN` (минимум 32 случайных символа) хранить только в переменной окружения сервера.
6. Установить `bookingEnabled=true`, пересобрать и развернуть сайт и API. В `/admin/` задать реальные интервалы и проверить одну тестовую заявку с согласованным тестовым номером.

Генерация ключа (результат не размещать в репозитории):

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node --env-file=.env server/index.mjs
```

В `.env` используются имена из `.env.example`. Приложение по умолчанию слушает только `127.0.0.1`. Проксируйте его через HTTPS reverse proxy. В Docker задан `HOST=0.0.0.0`; подключите постоянный том `/app/data`, ограничьте прямой доступ к порту и настройте прокси.

Порядок запуска в одном домене: задайте пустой `basePath`, правильные `origin` и `apiBase`, выполните сборку, затем запустите сервер. API также обслуживает `dist`. Поддомен API допустим; он должен быть в конфигурации сайта, а домен сайта — в списке разрешённых Origin.

## Расписание и работа диспетчера

Интервал принадлежит одному мастеру, виду техники, дате и времени. Один мастер не может быть одновременно назначен в два округа или на два вида техники. Клиенту доступны интервалы выбранного направления. При обновлении существующей SQLite-базы новые столбцы `appliance` добавляются автоматически; старые обращения и интервалы получают значение `washer`. Заявка удерживает выбранный интервал; статус `cancelled` освобождает его. Клиент видит, что визит требует подтверждения. Отмена устаревших заявок выполняется диспетчером, автоматического истечения брони нет. Перенос пока выполняется отменой и созданием новой записи, отдельного интерфейса переноса нет.

Ключ диспетчера передаётся в заголовке Authorization, хранится только в памяти текущей вкладки. Не вставляйте его в адресную строку. Это однопользовательский служебный доступ; роли сотрудников, 2FA и журнал аудита не реализованы. Для большой команды нужна следующая итерация авторизации.

База хранит имена, номера, согласия и вложения. Каталог `data/` должен быть закрыт от внешнего HTTP-доступа, защищён правами ОС и резервным копированием. Для согласованного удаления персональных данных используйте административные операции с SQLite на сервере. Не отправляйте базу в GitHub.

## SEO, фид и реклама

- До открытия страницы имеют `noindex`, robots.txt запрещает обход. После `bookingEnabled=true` сайт открывается для индексации; кабинет всегда нужно исключать.
- Sitemap: `/sitemap.xml`. На GitHub Pages robots.txt проекта находится в подкаталоге: для полноценного управления robots нужен собственный домен/корневое размещение. Meta robots сохраняет действие на каждой странице.
- Фид `/feed-services.yml` создаётся только при утверждённых данных. Используется договорная цена, чтобы не выдавать примерный диапазон за точное предложение. Проверить файл в Вебмастере и пройти модерацию: https://yandex.ru/support/webmaster/ru/search-appearance/offices/about
- IndexNow: задать собственный `indexNowKey`, пересобрать сайт, затем `node indexnow.mjs https://ваш-домен/новая-страница/`. Это уведомление, не гарантия индексации.
- После настройки `metrikaId` подготовить цели в Метрике. Ретаргетинг на завершивших диагностику настраивается в Директе отдельно, исключая полученные обращения. Статусы `qualified` и `paid` доступны в CSV для последующей CRM-интеграции; автоматического импорта офлайн-конверсий нет.
- Новая статья добавляется в массив `articles` в `src/data.mjs`; сборка создаёт HTML, JSON-LD и добавляет URL в sitemap.

## Проверки и ограничения

Автотесты проверяют денежные расчёты, отрицательные/пустые значения, номера, состав статей, фид, закрытый приём, доступ к кабинету, согласие, дедупликацию, конфликт интервалов, отмену и публикацию кейса. Набор из 9 тестов также проверяет категории, соответствие бренда технике и запись только в подходящий интервал. Проверка сборки: 21 HTML-файл, включая 404. В предыдущей версии в браузере проверены главный экран, мобильный вид, расчёт 9000/45000=20%, код LG OE и фильтр блога. Новая версия с тремя направлениями не прошла повторную визуальную проверку: доступное подключение к браузеру не работает.

OCR требует сети для программы/языковой модели и может ошибаться на сегментных дисплеях; ручное подтверждение обязательно. Фотография не отправляется в облачный AI. Данные клиентов не должны храниться в GitHub Issues или открытых файлах. Применены ограничения тела запроса, проверка изображений, CORS, постоянное сравнение секрета и SQL-параметры. Для продакшена дополнительно нужны резервное копирование, мониторинг, регламент обработки заявок и ограничения запросов на reverse proxy. Лимитер в коде хранится в памяти одного процесса.
